# Domain Model Diagram

You produce and maintain `docs/domain.md`: one Mermaid diagram showing **all** entities
from **all** specs in `docs/specs/`, plus their relationships. The specs are the single
source of truth — you never invent an entity, attribute, or relationship that no spec
states, and you never drop one that a spec does state.

## Procedure

### 1. Collect

Glob `docs/specs/*.md` and read **section 5 (Domain Model)** of every one — subsections
`5.1 Entities`, `5.2 Relationships`, `5.3 Value Objects`, `5.4 Domain Rules and Invariants`.
Read the whole section; attributes live in tables but qualifiers ("derived, never stored",
"referenced, not owned", "owned by story 009") live in the prose around them.

If `docs/specs/` is empty or has no section 5 anywhere, stop and tell the user there is
nothing to model yet — do not write a placeholder file.

When invoked with an argument (a story number like `012` or a slug), still read every
spec — the diagram is always whole-domain — but focus your reporting and your diff on
what that spec changed.

### 2. Merge

The same entity appears in several specs, usually once as owner and several times as
"referenced, not owned". Produce **one** node per entity:

- **Owner** = the spec that defines the entity in full (its own `#### Entity` block with
  a complete attribute table, not marked as referenced). Record it; it goes in the
  entity's catalog row.
- **Attributes** = the union across specs. A referencing spec that lists only `id` and
  `name` is narrowing its own view, not contradicting the owner.
- **Conflicts** — same attribute, different type or contradictory constraints in two
  specs — are the interesting output. Take the owning spec's version for the diagram and
  list the conflict under *Open Questions* in the file, citing both specs.
- Entities named in a relationship but never defined anywhere (e.g. a story not yet
  specced) get a node with no attributes and a note that no spec defines them yet.

Match names exactly as the specs write them (`TimeEntry`, not `Time Entry`). If two specs
use different names for the same concept, that is a ubiquitous-language bug — pick the
owner's name, and report it.

### 3. Diagram

One `erDiagram` for the whole domain. Mermaid ER syntax is strict:

- Attribute lines are `type name` plus optional key (`PK`, `FK`, `UK`) and a quoted
  comment: `UUID personId FK "immutable, set from session"`.
- Types must be single tokens — map spec types to `UUID`, `string`, `integer`, `decimal`,
  `boolean`, `date`, `time`, `datetime`, `enum`. Never emit a type with a space or
  parentheses in it.
- Put the constraint text in the quoted comment, keeping it to what a reader needs:
  required/optional, ranges, uniqueness. Drop filler like "PK, generated" — `PK` says it.
- Mark derived attributes in the comment (`"derived: endTime - beginTime"`), since the
  distinction between stored and computed is the kind of thing this diagram exists to
  make visible.

Cardinality, translated from the relationship prose:

| Spec says                     | Mermaid                            |
| ----------------------------- | ---------------------------------- |
| one-to-many, child required   | `Parent ||--o{ Child : "owns"`     |
| one-to-many, child optional   | `Parent |o--o{ Child : "has"`      |
| many-to-many                  | `A }o--o{ B : "assigned to"`       |
| one-to-one                    | `A ||--|| B : "is"`                |

Always label the relationship with the verb the spec used. If the spec's wording does not
settle optionality, choose the looser cardinality and note it as an open question rather
than inventing a constraint.

Value objects: include them, drawn with the entity that owns them and labelled
`"value object"` on the relationship, so they are visibly distinct from entities. If a
value object is not a separate row (e.g. `TimeRange` is really two columns on
`TimeEntry`), say so in the notes under the diagram instead of drawing a false table.

Keep the diagram readable: group related entities by declaring them in clusters, and put
the high-traffic entities (the ones most relationships touch) first.

### 4. Write `docs/domain.md`

````markdown
# Domain Model

<!-- Generated by the /domain-model skill from docs/specs/. Edit the specs, not this file. -->

Consolidated view of every entity across all feature specs. Each entity's authoritative
definition lives in its owning spec — follow the links for constraints and invariants.

## Diagram

```mermaid
erDiagram
...
```

## Entities

| Entity | Owning spec | Description | Also referenced by |
| ------ | ----------- | ----------- | ------------------ |

## Value Objects

| Value object | Owning spec | Belongs to | Description |
| ------------ | ----------- | ---------- | ----------- |

## Cross-Spec Invariants

<!-- Rules from 5.4 that span more than one spec, or that constrain a relationship
     rather than a single entity. Single-spec rules stay in their spec. -->

## Open Questions

<!-- Naming conflicts, contradicting attribute definitions, undefined entities,
     cardinality the specs leave ambiguous. Empty section is a good outcome — say
     "None." rather than deleting the heading. -->
````

Link every spec reference relatively, e.g. `[spec 001](specs/001-daily-time-entry.md)`,
since `domain.md` sits one level above `specs/`.

### 5. Update, don't clobber

If `docs/domain.md` already exists, read it first and rewrite it — the file is generated,
so a full rewrite is correct, but you must:

- Preserve any content under headings you did not generate (a human may have added
  sections); re-emit them unchanged at the end.
- Tell the user what actually changed: entities added or removed, attributes changed,
  relationships changed, open questions opened or closed. A diff summary in three or four
  bullets, not a re-narration of the file.

If the rewrite would remove an entity that a previous version had, say so explicitly and
name the reason (spec deleted, entity renamed, entity merged) — a silently vanishing
entity is how a domain model rots.

### 6. Verify before finishing

- Every entity in the catalog table appears in the diagram, and vice versa.
- Every relationship connects two entities that are declared in the diagram.
- No attribute type contains a space, comma, or parenthesis.
- Every spec in `docs/specs/` with a section 5 contributed at least one entity, or you
  can say why it did not.

State the path and the entity/relationship counts when done.

## Tone

Report like a modeller, not a generator. The valuable output is not the diagram — it is
the list of places where the specs disagree with each other. Lead with those.
